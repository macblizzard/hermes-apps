# Deployment (this host)

What runs, where, and how to undo it. Written after the first real deployment on `hermes`
(100.86.19.1), 5 Nov 2026.

## Topology

```
 iPhone / Mac  ──WireGuard (tailnet)──┐
                                       ▼
        https://hermes.corvus-vibes.ts.net:8443   ← tailscale serve, valid cert, tailnet only
                                       │
                                       ▼
                       127.0.0.1:8787  hermes-native-bridge.service
                                       │  JSON-RPC relay (1 MiB cap, method allow-list)
                                       ▼
                       127.0.0.1:9120  hermes-native-gateway.service
                                       │  `hermes -p cody dashboard` → the TUI gateway at /api/ws
                                       ▼
                            every profile = every bot (multiplex is on by default)
```

There is **no public listener**. Tailscale is the wall; `tailscale serve` supplies TLS from a
publicly-trusted CA, so the apps need no ATS exception and no certificate pinning.

## Units

| Unit | What it is | Notes |
|---|---|---|
| `hermes-native-gateway.service` | dashboard on `127.0.0.1:9120`, profile `cody` as the selected one | serves **all** profiles (`gateway.multiplex_profiles` defaults true) |
| `hermes-native-bridge.service` | the bridge on `127.0.0.1:8787` | `ProtectHome=read-only`, no new privileges |
| `hermes-gateway.service` | **NOT OURS** — the messaging gateway (Telegram/Discord/…) | never write this unit name; see the warning below |

### Warning: the unit name that already exists

`hermes-gateway.service` is the **messaging gateway**, generated by Hermes itself and running
`/root/scripts/hermes-gateway-runtime.sh gateway run`. Writing that filename replaces the unit for
the next reboot while the running process keeps the old configuration — so the breakage is invisible
until a restart. During this deployment it was overwritten by accident and restored with
`hermes gateway install` + the original property set from `systemctl show`. Hence the `hermes-native-*`
prefix on our units: never reuse a `hermes-*` name Hermes itself may generate.

## Secrets

`/etc/hermes-bridge/secrets.env` (mode 0600, dir 0700) holds two variables with the **same** value:

```
HERMES_DASHBOARD_SESSION_TOKEN=<43-char random>   # the gateway accepts it on its loopback WS
HERMES_BRIDGE_GATEWAY_TOKEN=<same>                # the bridge presents it upstream
```

The gateway URL and token never reach a client: the apps only ever hold *device* credentials.

Rotate by writing a new value to both variables and `systemctl restart hermes-native-gateway
hermes-native-bridge`. Every connected device must re-pair afterwards, because the bridge's refresh
tokens are independent — revoking devices is separate from rotating the host token.

## First pairing

Pairing codes are minted **on the host only**; a request that arrives through `tailscale serve` is
refused even though its peer address looks like loopback (it carries proxy headers).

```bash
curl -s -X POST http://127.0.0.1:8787/v1/pair/start | jq
# { "code": "21748145", "expires_at": …, "host": "hermes.corvus-vibes.ts.net", "protocol_version": 1 }
```

The app redeems that code over HTTPS with an Ed25519 public key (32 bytes, base64), and gets a
`device_id` + refresh token. **The key must be exactly 32 bytes** — a 33-byte value is rejected,
correctly.

## Measured (5 Nov 2026, this host)

| Path | Result |
|---|---|
| `ping` over public TLS (loopback→serve→bridge→tls) | min 4.1 / median 7.0 / max 9.4 ms |
| `ping` through the bridge, loopback only | 0.81 / 0.84 / 0.92 ms |
| `prompt.submit` → first `message.delta` (replay gateway) | 0.9 ms |
| `profiles.list` | 15 bots |
| `session.list` per bot (`include_hidden: true`) | cody 1, jason 5, anika 2, atlas 1 |

`session.list` **must** carry `include_hidden: true` for a bots surface: without it `cody` returns 0
rows even though its database holds 16 sessions (they are `oneshot`/`subagent`/`desktop` sources).

## Uninstall

```bash
systemctl disable --now hermes-native-bridge.service hermes-native-gateway.service
rm /etc/systemd/system/hermes-native-{bridge,gateway}.service
tailscale serve --https=8443 off
systemctl daemon-reload
rm -rf /opt/hermes-apps /var/lib/hermes-bridge /etc/hermes-bridge
```

Do **not** touch `hermes-gateway.service` while doing this — that is the messaging gateway.

## The rule that caused the second collision

**Hermes allows exactly one machine-level dashboard server per host.** Whichever process binds it
first owns the slot, and every later `hermes dashboard` refuses to start with

```
Refusing to start: this host is already served by PID 1256270 (127.0.0.1:9120; profiles: default,
anika, aria, ...). You asked for --port 9119 (the host owner is on port 9120).
```

Measured on this host: `hermes-native-gateway` took the slot at 14:26:36; a dashboard start on
`:9119` was refused at 14:26:50; tailscaled logged `dial tcp 100.86.19.1:9119: connect: connection
refused` at 14:34:25; a `socat` forwarder (`hermes-dashboard-forward.service`, `:9119 → 127.0.0.1:9120`)
was installed at 14:34:51 to restore that surface. It works, but it means any other dashboard surface
now terminates in *this* process — so restarting `hermes-native-gateway` briefly drops it.

Consequences to respect:

- Check `hermes dashboard --status` before starting this gateway on a host someone else uses.
- Restarting it is a user-visible event for every forwarded dashboard surface — announce it.
- `--isolated` gives a dedicated server scoped to one profile, freeing the host slot, but the app
  then loses the all-bots view (`profiles.list` would still answer, sessions would not).
